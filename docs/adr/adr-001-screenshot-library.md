# ADR 001: スクリーンショット取得ライブラリの選定

## Status

Accepted

## Context

sss-scene-captureは、開発者本人が使うWindows専用のCLIツールである。セッション開始時にプライマリーモニター全体のスクリーンショットを1枚撮り、PNGとして保存する。ストーリーマップには、後続タスクとして指定ウィンドウのスクリーンショットを撮る機能もある。

スクリーンショットの取得にはOSのAPIを呼ぶ必要がある。Rustの標準ライブラリにはその機能がない。外部クレートを選ぶ必要がある。

取得した画像は`image`クレートの型で扱いたい。PNGへの保存を`image`クレートに任せられるためである。

取得ライブラリはコードの中心に入り込む。後から差し替えると、取得処理とテストの両方を書き直すことになる。このため、最初に選定を記録しておく。

## Decision

スクリーンショットの取得には`xcap`クレートを採用する。`wgc`フィーチャーを有効にし、Windows Graphics Capture API（WGC）で取得する。

```toml
[dependencies]
xcap = { version = "0.9", features = ["wgc"] }
```

`xcap`はモニター単位とウィンドウ単位の両方の取得を提供する。`Monitor::all()`でモニターの一覧を得て、`is_primary()`でプライマリーモニターを選ぶ。`capture_image()`は`image`クレートの`RgbaImage`を返す。ウィンドウ取得には`Window::all()`を使う。

WGCを選ぶ理由は、後続タスクの指定ウィンドウ取得にある。WGCはDWMの合成結果を読むので、DirectXやブラウザのGPU描画もウィンドウ単位で撮れる。`xcap`のデフォルトであるGDIでは、ウィンドウ単位のGPU描画が黒くなることがある。

取得した画像は`RgbaImage`のまま扱う。PNGへの保存は`image`クレートの`save`に任せる。

## Alternatives

### Alternative 1: win-screenshot

Windows専用の小さなクレートである。モニター全体と指定ウィンドウの両方を撮れる。依存は`windows`クレートだけで軽い。返り値は独自の構造体だが、`RgbaImage::from_raw`を1回呼べば`image`の型に変換できる。

欠点は2つある。第一に、取得方式がGDIのみで、WGCを選べない。READMEにも、GPU描画のウィンドウが黒くなる既知の問題がある。第二に、`capture_display()`は全モニターをまとめて撮るので、プライマリーモニターだけを選ぶAPIがない。

この2点から採用しなかった。

### Alternative 2: windows-capture

WGCを使う、Windows専用の高速なクレートである。取得方式は本ADRの決定と同じである。

欠点は、動画録画向けにフレームをコールバックで受け取る設計になっている点である。静止画1枚を撮るには、ハンドラーを実装してセッションを開始し、最初のフレームで停止する手順が必要になる。

`xcap`なら同じWGCを1回の関数呼び出しで使える。このため採用しなかった。

### Alternative 3: xcapをGDI（デフォルト）で使う

`wgc`フィーチャーを付けずに`xcap`を使う方法である。モニター全体の取得ではDWMの合成結果を読むので、DirectX描画も映る。今回のタスクだけならこれで足りる。

しかし、後続のウィンドウ取得タスクでは、GPU描画のウィンドウが黒くなる。そのときにフィーチャーを切り替えるより、最初からWGCにしておくほうが挙動が一貫する。このため採用しなかった。

### Alternative 4: screenshots

以前広く使われていたクレートである。作者が`xcap`へ移行し、現在は非推奨である。採用しなかった。

### Alternative 5: Windows APIを直接呼ぶ

`windows`クレートでWGCやGDIを直接呼ぶ方法である。依存を最小にできる。しかし、Direct3Dデバイスの作成、フレームプールの管理、テクスチャからCPUメモリへのコピーを自分で書く必要がある。個人ツールにはコストが高い。採用しなかった。

## Confidence Level

高い。

`xcap`はモニターとウィンドウの両方を撮れ、`image`の型を直接返す。今回のタスクと後続タスクの両方を満たす。WGCはWindows 10 1803以降の標準APIで、Windows 11の開発機では問題なく動く。

次の状況になったら見直す。

- 排他フルスクリーンのアプリを撮る必要が出たとき。WGCはDWMを通らない描画を撮れない。DXGI Desktop Duplicationへの切り替えを検討する。
- `xcap`の`wgc`フィーチャーに不具合が見つかり、修正が見込めないとき。`windows-capture`への切り替えを検討する。
- 連続キャプチャや動画録画が必要になったとき。フレームストリーム設計の`windows-capture`のほうが向いている。

## Consequences

### 良い影響

- プライマリーモニターの選択、ウィンドウの列挙、画像の取得を1つのクレートで済ませられる。
- 取得結果が`RgbaImage`なので、PNG保存は`image::save`の1行で書ける。
- 将来の指定ウィンドウ取得で、GPU描画のウィンドウも黒くならずに撮れる。

### 悪い影響

- クロスプラットフォーム対応の分、Windows専用クレートより依存とビルド時間が増える。
- 取得処理はOSに直接触るので、通常の単体テストで結果の内容を検証しにくい。テストでは、実機で取得した画像の幅と高さが0でないことなど、環境に依存しにくい性質を確認する形になる。
- Windows 10で実行した場合、WGCの黄色い枠が画面に出る。開発機はWindows 11なので当面の影響はない。

### 中立な影響

- `image`クレートが推移的依存として入る。PNG以外の形式で保存したくなった場合も追加の依存は不要である。
- サウンド記録のライブラリ選定は別のADRで扱う。
