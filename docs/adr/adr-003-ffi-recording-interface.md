# ADR 003: 別言語向けの録音インタフェース

## Status

Accepted

## Context

sss-scene-captureのライブラリ部分は、Rustで書いたCLIツールから使うだけでなく、Javaなど別言語のアプリから呼ばれることを想定している。録音の開始と停止を外部から操作できる必要がある。

別言語から呼ぶには、C ABI（`extern "C"`）で関数を公開する。Cの世界に渡せるのは整数、ポインタ、C文字列だけである。今のRust側API（`Recording`構造体を返す`start_recording`と、それを所有権ごと受け取る`stop_recording`）は、そのままでは外に出せない。

FFIの境界には、Rustの所有権やライフタイムの検査が届かない。呼び出し側が停止を2回呼ぶ、開始したまま忘れる、無効な値を渡す、といった誤用をコンパイル時に防げない。誤用がメモリ破壊につながる設計は避けたい。

呼び出し側のスレッドも自由に選ばれる。JavaはFFIの呼び出しを任意のスレッドから行うので、開始と停止が別のスレッドから来る。cpalの`Stream`はプラットフォームによって`Send`ではなく、作ったスレッドと別のスレッドで破棄することを想定していない。

録音データはf32のサンプル列で、1時間で1GBを超える。FFI越しに大きな配列を受け渡すのは、メモリの所有権と解放の責任が曖昧になりやすい。

ADR-002で録音方式を決めた時点では、Rust内で完結するAPIしか考えていなかった。外部公開の形は、後から変えると呼び出し側のコードも書き直しになる。このため、Rust側のAPIが小さいうちに決める。

## Decision

FFIは、C ABIの関数と整数IDのハンドルで公開する。

### 内部構造: 録音専用スレッド

`start`は録音専用のスレッドを1本立てる。cpalの`Stream`はこのスレッドの中で作り、このスレッドだけが所有する。スレッドはチャンネルの`recv()`で停止命令を待つ。`stop`はチャンネルで命令を送り、`JoinHandle`で終了を待つ。スレッドは`recv()`から抜けて`Stream`を破棄し、録音が止まる。

外に持ち出すのは`Sender`と`JoinHandle`だけである。どちらも`Send`なので、どのスレッドから`stop`を呼んでも安全である。

### ハンドル: 整数IDとレジストリ

`start`は`u64`のIDを返す。Rust側は`static`のレジストリ（`Mutex<HashMap<u64, Recorder>>`）でIDと録音の対応を持つ。所有権はレジストリにあり、呼び出し側はIDの数値を持つだけである。IDは単調増加で、再利用しない。

`stop(id)`はレジストリからIDを取り除いて停止する。無効なIDや停止済みのIDはエラーコードで返す。呼び出し側が停止を2回呼んでも、メモリは壊れない。

### 録音データの受け渡し: ファイル経由

`stop`は保存先のファイルパスをC文字列で受け取り、Rust側でWAVに書く。サンプル列をFFI越しに返さない。呼び出し側は書かれたファイルを読む。

### 公開する関数

```rust
#[unsafe(no_mangle)]
pub extern "C" fn sss_start_recording() -> u64;                 // 0は失敗
#[unsafe(no_mangle)]
pub extern "C" fn sss_stop_recording(id: u64, wav_path: *const c_char) -> i32;  // 0は成功
```

エラーは戻り値の整数で表す。Rustのpanicは`std::panic::catch_unwind`で境界の内側に止め、エラーコードに変える。panicが`extern "C"`の境界を越えるのは未定義動作である。

### 層の分け方

Rustネイティブの`start_recording`/`stop_recording`は残し、テストはこちらで書く。FFI関数は`src/ffi.rs`に置き、ネイティブAPIを呼ぶ薄い翻訳層とする。`Cargo.toml`の`crate-type`は`["cdylib", "rlib"]`とし、共有ライブラリとRustライブラリの両方を作る。

## Alternatives

### Alternative 1: 不透明ポインタをハンドルにする

`start`が`Box::into_raw`で`*mut Recorder`を返し、`stop`が`Box::from_raw`で取り戻して破棄する。C言語のライブラリで最も一般的な形で、Rust側にレジストリが要らない。

欠点は、所有権を呼び出し側の正しい振る舞いに預ける点である。`stop`を2回呼ぶと二重解放になり、無効なポインタを渡すとメモリを壊す。防御はJava側のフラグに頼ることになる。整数IDならこれらをエラーコードで返せる。採用しなかった。

### Alternative 2: ハンドルを持たないグローバルな開始と停止

`start()`と`stop()`に引数を持たせず、Rust側が`static`の`Option<Recorder>`で「いまの1本」を持つ。実装は最も小さい。このアプリは1セッションずつなので、要件は満たす。

しかし、`stop`がどの録音を止めるかを指定できないので、録音を2本以上区別して扱えない。Java側で2つのオブジェクトが同じライブラリを使うと、片方の`stop`がもう片方を止める。テストも1つの状態を共有する。整数IDとの実装コストの差は数十行で、後から変えるほうが高くつく。採用しなかった。

### Alternative 3: `Recording`を今のスレッドで持ち、停止時に別スレッドから破棄する

録音専用スレッドを立てず、`Stream`をレジストリに直接入れる。構造が1段減る。

しかし、cpalの`Stream`はプラットフォームによって`Send`ではなく、`Mutex`の中に入れてスレッド間で共有できない。作ったスレッドと別のスレッドで破棄する動作も想定されていない。Javaは任意のスレッドから`stop`を呼ぶので、この前提が成り立たない。採用しなかった。

### Alternative 4: サンプル列をFFI越しに返す

`stop`が`f32`の配列へのポインタと長さを返し、呼び出し側が読み終えたら解放関数を呼ぶ。ファイルを経由しないので、呼び出し側で加工したい場合に柔軟である。

しかし、解放の責任が呼び出し側に移り、忘れると漏れる。1時間で1GBを超えるデータの寿命を境界の両側で管理することになる。今の要件はWAVとして保存することだけなので、Rust側で書いてしまうほうが単純である。採用しなかった。

### Alternative 5: JNIで公開する

`jni`クレートで`Java_..._start`のような関数を書く。Java 21以前でも使える。

しかし、関数名と引数がJavaのクラス構造に縛られ、Rust側にJava専用のコードが入る。他の言語からは使えない。C ABIならJava 22以降のFFM APIで直接呼べ、PythonやC#からも同じ関数を使える。採用しなかった。

## Confidence Level

高い。

整数IDとレジストリ、録音専用スレッドとチャンネル、ファイル経由の受け渡しは、いずれもC ABIのライブラリで長く使われてきた形である。RustのFFIガイドラインとも一致する。Java側はFFM API（Java 22で正式化）で追加コードなしに呼べる。

次の状況になったら見直す。

- 録音データをファイルに書かず、呼び出し側でリアルタイムに処理する要件が出たとき。サンプル列を境界越しに渡す設計（Alternative 4）か、コールバック登録の設計が必要になる。
- 呼び出し側がJavaに限られ、かつJava 21以前を使う必要が出たとき。FFM APIが使えないので、JNIかJNAの層を追加する。C ABIの関数はそのまま使える。
- 録音以外の機能（スクリーンショット、セッション全体の開始と停止）もFFIで公開するとき。同じIDとレジストリの形に揃えるか、セッション単位のハンドルに変えるかを別ADRで決める。
- cpalの`Stream`が全プラットフォームで`Send`になったとき。録音専用スレッドを外せる可能性がある。ただし、外さなくても動作に問題はない。

## Consequences

### 良い影響

- 呼び出し側の誤用（停止の二重呼び出し、無効なID）がエラーコードで返り、メモリを壊さない。
- 開始と停止をどのスレッドから呼んでもよい。`Stream`の`Send`制約が外部に漏れない。
- 録音を複数本、区別して持てる。Java側で複数のオブジェクトが同じライブラリを使っても干渉しない。
- C ABIなので、Java以外の言語からも同じ関数を呼べる。
- Rustネイティブの`start_recording`/`stop_recording`とそのテストはそのまま残る。FFI層は薄い翻訳で、テストの主体はネイティブAPIのままである。

### 悪い影響

- 録音専用スレッドとチャンネルの分だけ、内部構造が1段増える。`Recording`の内部は「録音スレッドへの`Sender`と`JoinHandle`」に変わり、今の`Stream`を直接持つ形からリファクタリングが必要になる。
- レジストリは`static`のグローバル状態である。テストでレジストリを使う場合、テスト間で共有される。ネイティブAPIのテストはレジストリを通らないので、影響はFFI層のテストに限られる。
- エラーの詳細（どのデバイスで何が失敗したか）が整数コードに潰れる。必要になったら、最後のエラーメッセージを取得する関数を追加する。
- `catch_unwind`でpanicを止めるため、Rust側のバグが呼び出し側からはエラーコードにしか見えない。

### 中立な影響

- IDは`u64`で単調増加。実用上は枯渇しない。0は「失敗」の意味に予約する。
- ファイルパスはUTF-8のC文字列として受け取る。Windowsの非ASCIIパスは、Java側がUTF-8で渡せば問題ない。
- 「Enterキーで停止」のCLI機能は、FFIを経由せずネイティブAPIで実装する。FFIは別言語向けの入り口であり、CLIの構造には影響しない。
- 共有ライブラリ（`cdylib`）とRustライブラリ（`rlib`）の両方をビルドするので、ビルド成果物が増える。
