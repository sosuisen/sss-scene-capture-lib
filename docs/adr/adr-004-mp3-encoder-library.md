# ADR 004: MP3エンコードライブラリの選定

## Status

Accepted

## Context

sss-scene-captureは、停止後にサウンドをファイルに保存する。保存形式にはWAVとMP3の2つがある。WAVは32bit floatで書く（ADR-002）。MP3は変換して書く。どちらを使うかは利用者が選ぶ。どちらかが基本という位置づけはない。

2つの形式は性質が異なる。WAVは無劣化だが、48kHzステレオで1分あたり約23MBになる。MP3は非可逆圧縮だが、同じ時間で1〜2MBに収まる。用途によって適切な形式が変わるので、両方を用意する。

MP3のエンコードは複雑で、自前で書く対象ではない。ライブラリを選ぶ必要がある。ADR-002ではこの選定を別のADRに先送りしていた。

選択肢は2系統ある。ひとつは、Cで書かれた実績あるエンコーダ（LAME）をバインディング経由で使う方法である。もうひとつは、純Rustのエンコーダを使う方法である。純RustのMP3エンコーダは2026年7月に初めて登場し、この時点で実績は2か月分しかない。一方、LAMEはビルドにCコンパイラを要し、ライセンスがLGPLである。

ライブラリはRust側のAPI（`save_wav`と同じ形の`save_mp3`）の裏に隠れるので、後からの差し替えは難しくない。この点は、実績の乏しいライブラリを試す判断を後押しする。

ADR-003でJavaなど別言語から共有ライブラリとして呼ぶ方針を決めている。ビルドと配布が単純であるほど、この方針と相性がよい。

このプロジェクトは個人が趣味で作っているツールである。音質の厳密な保証や配布時のライセンス対応より、ビルドの単純さと新しいものを試す面白さを優先してよい。

## Decision

MP3のエンコードには`rusty_mp3`クレートを採用する。

```toml
[dependencies]
rusty_mp3 = "0.8"
```

### ライブラリの構成

`rusty_mp3`は純RustのMP3エンコーダとデコーダである。依存クレートはなく、CコードもFFIもない。`cargo build`だけでビルドが完結し、Cコンパイラは不要である。ライセンスはApache-2.0で、配布時の追加条件はない。

### 入力の受け渡し

エンコーダには、cpalから受け取った`f32`のサンプル列をそのまま渡す。`push_pcm_f32(interleaved, channels, sample_rate)`は`[L, R, L, R, ...]`の並びを直接受け取る。整数への変換は行わない。モノラルもステレオも同じ関数で扱える。

### エンコード設定

サンプルレートとチャンネル数は録音デバイスの値をそのまま使う。ビットレートは192kbpsのCBRとする。個人ツールで容量より音質を優先するため、高めの設定を既定にする。設定は`save_mp3`の内部に閉じた定数で、必要になったら引数に出す。

### APIの形

`save_wav`と同じ引数の`save_mp3`を公開する。

```rust
pub fn save_mp3(samples: &[f32], sample_rate: u32, channels: u16, path: &Path) -> Result<(), Box<dyn std::error::Error>>
```

流れは、`Mp3EncoderConfig`で設定を作り、`Mp3Encoder::new`でエンコーダを作り、`push_pcm_f32`で全サンプルを渡し、`finish()`で終端処理をしてから、`next_packet()`が`Eof`を返すまでフレームを取り出してファイルに書く。

### バージョンの固定

`rusty_mp3`は0.xで、APIが変わる可能性が高い。`Cargo.toml`ではマイナーバージョンまで指定し、更新は意図して行う。更新でAPIが変わった場合、影響は`save_mp3`の中に閉じる。

## Alternatives

### Alternative 1: `mp3lame-encoder`（LAME）

LAMEへの高レベルなバインディングである。LAMEは20年以上の実績を持つ事実上の標準MP3エンコーダで、音質の評価も確立している。`mp3lame-sys`がCソースを同梱し、ビルド時に一緒にコンパイルするので、実行時の外部依存はない。`f32`のインターリーブ入力も受け取れる。

欠点は2つある。ビルドにCコンパイラが要る点と、ライセンスがLGPLである点である。この環境ではMSVCが揃っているのでビルドは通るが、共有ライブラリとして他の環境でビルドするときに条件が増える。LGPLは個人利用では問題にならないが、配布時には利用者がLAME部分を差し替えられる形にする義務がある。趣味のプロジェクトとして、実績よりビルドの単純さと純Rustの新しさを優先し、採用しなかった。差し替え先の第一候補として残す。

### Alternative 2: `shine-rs`

Shineを純Rustに移植したエンコーダである。Shineは組み込み向けに速度を優先した設計で、心理音響モデルを持たない。入力は`i16`のみで、CBRのみである。

`f32`から`i16`への変換が必要になり、音質もLAMEや`rusty_mp3`より低い。ライセンスはLGPLで、純Rustの利点であるライセンスの単純さも得られない。採用しなかった。

### Alternative 3: `oxideav-mp3`

純RustのMP3デコーダで、エンコーダは「最小限のCBR」と自ら位置づけている。エンコードを主目的にしたクレートではない。採用しなかった。

### Alternative 4: 外部の`ffmpeg`を起動して変換する

WAVを書いたあと、`std::process::Command`で`ffmpeg`を呼ぶ。Rust側にエンコードのコードが不要で、他の形式にも広げられる。

しかし、実行環境に`ffmpeg`がインストールされている必要がある。ADR-003で共有ライブラリとして別言語から呼ぶ方針を決めており、呼び出し側の環境に外部プログラムを要求したくない。採用しなかった。

### Alternative 5: MP3以外の圧縮形式にする

Opus（`audiopus`）やFLAC（`flacenc`、純Rust）なら、より成熟した純Rust実装や、より高い圧縮効率が得られる。

しかし、ストーリーマップの要件はMP3である。MP3は再生環境を選ばず、Javaを含む他言語のライブラリも豊富である。形式の変更は要件の変更なので、このADRの範囲外とする。採用しなかった。

## Confidence Level

中程度。

`rusty_mp3`は登場から2か月で、バージョンも0.xである。APIの変更や未発見の不具合に遭う可能性は、LAMEより高い。一方、`save_mp3`の中に閉じているので、問題が出たときの差し替えコストは小さい。趣味のプロジェクトとして許容できる範囲である。

次の状況になったら見直す。

- 生成したMP3が一部の再生環境で再生できない、または音質に明らかな問題があるとき。Alternative 1の`mp3lame-encoder`に差し替える。
- `rusty_mp3`の更新が止まったとき、または更新のたびにAPIが大きく変わって追従が負担になったとき。同じくAlternative 1に差し替える。
- 配布先の環境でCコンパイラの用意が簡単だと分かり、かつ音質の保証が必要になったとき。LAMEを選び直す理由になる。
- 純Rustの別のエンコーダが成熟し、`rusty_mp3`より実績を積んだとき。そちらへの乗り換えを検討する。

## Consequences

### 良い影響

- `cargo build`だけでMP3のエンコードまでビルドが完結する。Cコンパイラや外部プログラムの用意が要らない。
- ライセンスがApache-2.0なので、共有ライブラリとして配布するときにLGPLの条件を考えなくてよい。
- cpalから受け取った`f32`のサンプル列をそのまま渡せる。`save_wav`と`save_mp3`は同じ引数で、呼び出し側は形式の違いを意識しない。
- 依存クレートがゼロなので、依存の連鎖によるビルド時間の増加や脆弱性の混入が起きにくい。

### 悪い影響

- 実績が2か月分しかない。音質や互換性の問題が見つかる可能性がLAMEより高い。
- 0.xのため、更新でAPIが変わることがある。`Cargo.toml`でマイナーバージョンまで固定し、更新は意図して行う必要がある。
- 音質をLAMEと比べた公開データがない。気になる場合は自分で聴き比べることになる。
- エンコードは純Rustで、LAMEほど最適化されていない可能性がある。長時間の録音では変換に時間がかかるかもしれない。

### 中立な影響

- WAVとMP3のどちらを書くかを選ぶ手段（引数、設定、両方書くなど）は、このADRでは決めない。CLIの`main.rs`とFFIの層で、それぞれの利用者に合う形を決める。
- MP3の設定は192kbpsのCBRで固定する。VBRや他のビットレートが必要になったら、`save_mp3`の引数として出す。
- `rusty_mp3`はデコーダも含むが、このプロジェクトでは使わない。
- 差し替え先の第一候補は`mp3lame-encoder`である。`save_mp3`のテストがそのまま受け入れテストになる。
